## 引言

随着 Agent 系统从“单轮问答”走向“多步骤执行”，一个问题开始变得越来越重要：模型拿到工具之后，应该按什么流程完成任务。

仅有工具调用能力并不足以支撑复杂工作流。Agent 可能已经具备读写文件、查询数据库、调用 API 的能力，但面对“做一次代码审查”“生成一份测试报告”“整理技术调研结论”这类任务时，仍然需要明确的执行步骤、输出标准和可复用模板。`Skill` 正是在这样的背景下出现的。

本文从工程视角出发，梳理 Skill 的定义、结构、加载机制，以及它与 Prompt、Function Calling、MCP 之间的关系。

## 什么是 Skill

`Skill` 可以理解为 Agent 的知识与流程封装单元。它不是单独的一段提示词，也不是某个临时命令，而是一个能够被 Agent 自动发现、按需加载并持续复用的能力包。

从形式上看，一个 Skill 往往是一个目录，目录中至少包含一份 `SKILL.md`，并可以按需携带脚本、模板、参考文档和其他资源。它解决的核心问题不是“模型能不能调用工具”，而是“模型拿到工具之后，应该如何稳定地完成某一类任务”。

如果把 Agent 看成一个正在执行任务的系统，那么：

- Tool 负责提供动作能力
- Skill 负责提供知识、步骤和规范

因此，Skill 更接近“可执行任务说明书”，而不是简单的 prompt 片段。

## 为什么需要 Skill

在没有 Skill 的情况下，很多团队会反复遇到同一类问题：

- 每次开新对话，都要重新贴一遍长提示词
- 同一类任务在不同人手里，输出标准不一致
- 提示词版本无法统一维护
- 模型知道“可以做什么”，但不知道“应该怎么做”

例如代码审查场景里，团队往往希望 Agent 按固定步骤工作：

1. 先理解变更范围
2. 再检查功能正确性
3. 然后检查安全与性能问题
4. 最后按统一模板输出结果

如果这些约束只存在于临时 prompt 中，那么它们既不稳定，也难以复用。Skill 的意义就在于把这类反复使用的知识和流程沉淀下来，使 Agent 在遇到相关任务时，能够加载同一套规则执行。

## Skill 的基本结构

一个典型的 Skill 目录通常如下：

```text
code-review/
├── SKILL.md
├── scripts/
│   └── check_security.py
├── references/
│   └── review_standards.md
└── assets/
    └── report_template.md
```

其中最核心的文件是 `SKILL.md`。它通常包含两部分内容：

- 前置元数据：声明 Skill 的名称和一句话描述
- 正文指令：说明这个 Skill 适合解决什么问题、应按什么步骤执行、需要读取哪些资源

一个简化示例如下：

```md
---
name: code-review
description: 对代码进行结构化审查，检查功能、安全和性能问题
---

# 代码审查 Skill

## 指令

### 第一步：理解上下文
阅读改动内容，确认变更范围和目标模块。

### 第二步：执行检查
按功能正确性、安全性、性能和可读性四个维度逐项检查。

### 第三步：输出结果
使用 assets/report_template.md 生成结构化报告。
```

这种组织方式和普通 prompt 最大的区别在于：它不是一次性文本，而是一个可维护、可扩展、可版本管理的目录结构。

## Skill 的关键设计：渐进式加载

Skill 最有工程价值的一点，不是“能打包”，而是“不会一次性把所有内容都塞进上下文”。

如果一个 Agent 持有几十个 Skill，而每个 Skill 都包含较长的说明、模板和参考文档，那么把所有内容在启动时一次性加载进上下文，会造成明显的问题：

- token 消耗过大
- 无关信息过多
- 模型注意力被稀释
- 真正和当前任务相关的内容反而被淹没

因此，Skill 更合理的工作方式是渐进式加载，也可以理解为按需展开。这个过程通常分为三层：

### 第一层：只加载简介

Agent 启动时，通常只读取每个 Skill 的 `name` 和 `description`。这一层的目的不是执行任务，而是建立“当前有哪些可用能力”的能力索引。

### 第二层：命中后加载 `SKILL.md`

当用户任务与某个 Skill 相关时，Agent 才会进一步读取该 Skill 的正文指令，理解它的适用条件、执行顺序和输出规范。

### 第三层：执行时再读取附属资源

如果 `SKILL.md` 中引用了模板、脚本或参考资料，那么这些资源通常只会在真正执行到相应步骤时再加载。例如：

- 输出报告时再读取模板
- 需要核对规则时再读取参考文档
- 需要自动化处理时再调用脚本

这种设计的价值在于：**让 Skill 具备规模化复用能力，同时不过度占用上下文窗口。**

## Skill 不等于 Prompt

Skill 最容易被误解成“保存好的 prompt”，但两者并不等价。

Prompt 的特点通常是：

- 一次性使用
- 依赖人工输入或粘贴
- 缺少明确的目录结构
- 难以做资源化管理

Skill 则更接近一个结构化模块：

- 可以被 Agent 自动发现
- 可以按需加载
- 可以引用脚本、模板和文档
- 可以持续维护和版本化

换句话说，Prompt 更像一次性的任务指令，而 Skill 更像针对某类任务沉淀下来的可复用工作流。

## Skill 和 Slash Command 的区别

Slash Command 与 Skill 的共同点在于都能复用已有指令，但它们的触发方式并不相同。

- Slash Command 依赖用户显式触发，例如输入 `/review`
- Skill 更强调 Agent 的自动发现与自动加载

因此，Slash Command 更像“人工选择某个预设命令”，而 Skill 更像“系统根据任务上下文自动选择合适的工作模块”。

## Skill 和 MCP 的区别

Skill 与 MCP 经常被放在一起讨论，但两者解决的问题并不相同。

MCP 解决的是 **Agent 如何获得外部能力**。它把文件系统、数据库、API、浏览器等能力以标准协议方式暴露出来，使 Agent 可以访问外部世界。

Skill 解决的是 **Agent 获得能力之后，该如何按步骤完成任务**。它描述的是流程、知识、规范和输出方式。

从分工上看，两者是互补关系：

- MCP 提供“做事的手段”
- Skill 提供“做事的方法”

一个典型的配合方式是：

1. Skill 定义任务流程
2. 流程中的某些步骤需要调用 MCP 提供的工具
3. 工具返回结果后，Skill 再指导 Agent 如何继续下一步

因此，Skill 和 MCP 不是竞争关系，而是上下配合的两层机制。

## Function Calling、MCP、Skill 的三层关系

如果把 Agent 的工具使用能力拆开看，`Function Calling`、`MCP` 和 `Skill` 可以形成一个清晰的三层结构。

### 第一层：Function Calling

Function Calling 解决的是“模型如何表达一次工具调用”。它关心的是：

- 调哪个函数
- 参数是什么
- 执行结果如何回传

这是一种偏底层的调用表达机制。

### 第二层：MCP

MCP 在 Function Calling 之上，解决的是“工具如何标准化暴露给模型”。它关心的是：

- 工具有哪些
- 如何发现
- 如何跨客户端复用
- 如何以统一协议对接

这是一层偏工具协议的标准化封装。

### 第三层：Skill

Skill 位于更上层，解决的是“拿到这些工具之后，按什么流程完成某一类任务”。它关心的是：

- 任务步骤如何组织
- 需要哪些模板与参考资料
- 如何输出统一结果
- 如何把经验沉淀成可复用模块

如果用一句话概括三者关系，可以写成：

- Function Calling 是调用语言
- MCP 是工具接入协议
- Skill 是任务知识与流程封装

## Skill 适合解决什么问题

Skill 并不适合所有场景，它更适合以下几类重复性强、流程稳定、质量标准明确的任务：

- 代码审查
- 缺陷排查
- 测试报告生成
- 技术调研整理
- 文档规范化输出
- 项目交付清单检查

这些任务有一个共同特点：不只是“要完成”，还要求“按固定方式完成”。当团队希望把一套经验从个人习惯升级为稳定机制时，Skill 的价值就会非常明显。

## 写在最后

Skill 的出现，说明 Agent 系统的关注点已经从“能不能调用工具”进一步走向“如何稳定完成复杂任务”。

仅有工具能力，Agent 仍然缺少方法；仅有提示词，流程又难以复用。Skill 的作用，正是在这两者之间搭起一层可维护的知识与流程封装，使经验可以被模块化、被共享，也可以被系统按需调用。

如果只把 Skill 理解为“保存下来的 prompt”，会低估它的工程价值。更准确的理解是：**Skill 是 Agent 任务知识和执行流程的标准化载体。**
